# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Agent Office: a TypeScript Node.js web app that manages and visualizes Claude Code CLI agents in a 3D office (server on Hono, client on React + Zustand + three.js, built with Vite). See [README.md](README.md) for user documentation (features, controls, company structure/flow, permission modes).

## Conventions

- Code identifiers and comments are in English. **No user-facing string is hard-coded**: UI text, server messages/logs, agent prompts and tool activity all go through `src/shared/i18n/` (`tr.ts` is the source of truth for keys, `en.ts` must have the same keys — enforced by the type). The language is the `language` setting (first run: `LOCALE`/`LANG`, default Turkish). The default company (team names, roles, prompts) is localized separately in `src/shared/company/` (`tr.ts`, `en.ts`, built by `buildCompany(locale)`). Server code translates through `Translator`, client code through `useT()`; domain functions receive a `Translate` parameter. Adding a string = a key in both catalogs; adding a language = a new catalog + `LOCALES`.

## Commands

```bash
npm install
npm start                                   # vite build + server via tsx → http://localhost:4317
npm run dev                                 # Vite dev server (proxies /api to 4317); run the server with `npm run server`
npm run typecheck                           # tsc --noEmit (strict)
PORT=4400 npm start                         # different port
CLAUDE_BIN=/path/claude npm start           # give the claude CLI path manually
AGENT_OFFICE_DATA=/other/dir npm start      # try things without touching the real data/

npm test                                    # node --test, all src/**/*.test.ts (via tsx)
node --import tsx --test src/shared/layout.test.ts
node --import tsx --test --test-name-pattern="<name>" "src/**/*.test.ts"
```

There is no lint configuration; type checking is `npm run typecheck`.

## Layout

`src/server` (clean architecture, see below), `src/mcp` (agent MCP server), `src/shared` (pure modules shared by server, client and tests: `i18n`, `company`, `layout`, `catalog`, `chain`, `types`), `src/client` (Vite root, clean architecture, see below). The built client goes to `dist/client` and the server serves it from there.

## Architecture

**Server architecture (`src/server`).** Dependencies point inward: `interface` → `application` → `domain`; `infrastructure` implements the domain ports. `domain/` holds pure rules (`delegation.ts` chain logic, `prompts.ts`, `agent.ts`) and the port interfaces (`ports.ts`: `StateStore`, `Publisher`, `LogBook`, `Runner`). `application/` has the use-case services (`Agents`, `Tasks`, `Workspace`, plus `Notifier` and `PresenceBoard`; `Tasks` builds its parts: `Runs` drives the CLI process, `Reports` closes tasks and moves reports up the chain, `Merges` handles worktree work, `Blocks` says why a queue waits), which take ports through their constructors. `infrastructure/` has the JSON state store, file log book, SSE broadcaster, `ProcessRunner` and `providers/`. `interface/app.ts` is a Hono app (zod-validated bodies in `schemas.ts`; `DomainError` → HTTP status). `main.ts` is the composition root. State lives in `data/state.json` (`AGENT_OFFICE_DATA` changes the location); the office layout (`items`) is **not** persisted — `Agents.relayout()` regenerates it with `planOffice()` from the headcount and teams; only the office name and colors are stored. Live updates go out over SSE (`/api/events`).

**Every task is a CLI subprocess, chosen per agent (`agent.provider`).** When an agent is given a task (`Tasks.create` → `runNext`), `ProcessRunner` looks up the agent's provider (`infrastructure/providers/`: `claude`, `codex`, `cursor`), spawns the CLI with the provider's `buildArgs()` and feeds each stdout line to the provider's `createParser()`, which yields neutral events (`session`, `text`, `tool`, `tool-error`, `result`); `Tasks` only knows those events. They are broadcast live over SSE and written to `data/logs/<agent-id>.jsonl`. A log entry's long form (`detail`: a tool call's input, capped by `domain/logs.ts`) stays on disk: live events and recent logs carry only `hasDetail`, and `GET /api/tasks/:id/logs` (`LogBook.ofTask`, stream-read, newest `TASK_LOG_LIMIT` entries) serves the Flow tab's transcript, which `client/domain/transcript.ts` merges with the live feed. The `session` event's id is stored as `sessionId` and reused (resume) on the next task. New CLIs are added as a provider file plus one registry line.

**Isolation, schedules, outputs.** With `settings.worktrees` on, `Runs.runNext` asks the `Isolation` port (`infrastructure/gitIsolation.ts`) for the agent's own worktree (`.agent-worktrees/<slug>-<id>`, branch `agent/<slug>-<id>`, synced with the main branch before each run) and, on success, `integrate()`s it (commit + merge, aborted on conflict) **before** `finish()` sends the report, so whoever reads the work next sees it. Each run records `baseCommit`, `commit`, `branch`, `repo` and `merge` (`merged`, `unchanged`, `pending`, `conflict`, `rejected`) on the task; the task stays `done` on a conflict, but `reportPrompt` says the work is not in, and `Tasks.resolveConflict` gives it to the same agent in the same place of the chain (merging a branch closes the earlier conflicts on it). `Isolation.diff` backs `GET /api/tasks/:id/diff` (capped; `null` without commits, then the client shows `task.files`). With `settings.approveMerges` `integrate` stops after the commit and an approval of `kind: 'merge'` holds the report; its decision takes no agent run (`Tasks.decideMerge`: merge, or `discard` the branch back to `baseCommit`), and until then `runNext` starts nothing for that agent, so nothing is built on work that may be dropped. `application/schedules.ts` turns due `state.schedules` into ordinary tasks (`main.ts` ticks it every 30 s; timing rules in `domain/schedule.ts`). The `FileTree` port (`infrastructure/localFileTree.ts`) backs the read-only *Outputs* browser and must never read outside the working directory. `JsonStateStore` keeps hourly copies in `data/backups/` and restores from them if `state.json` is unreadable.

**Process lifecycle.** `ProcessRunner` starts each CLI as its own process group: `stop()` sends SIGTERM to the group, SIGKILL after a grace period, and `onExit` fires once regardless, even if the process or something it left behind never closes its output, so no run can hold an agent or a concurrency slot. On SIGINT/SIGTERM/SIGHUP `main.ts` calls `Runs.shutdown()`: no run starts any more, every run is stopped and left `running` (unless it finished properly), and the state is written. `Tasks.reconcile` closes those at the next start as `err.interrupted`; with `settings.resumeInterrupted` (off: it starts paid runs at boot) a task with a session goes back to the queue once (`task.resumed`) and runs with `resumePrompt`.

**Limits and approvals.** Before starting a queued task, `Runs.runNext` asks `domain/limits.ts` (`blockReason`: daily / per-agent budget from tasks' known cost since local midnight, running ones included, then `dailyRunMinutes` from run time, then provider holds and `maxConcurrent`); a blocked task stays queued with the reason as the agent's activity, and `Runs.pump()` retries everyone after each run, on limit changes and every 30 s. Cost is booked on the task and agent when a `result` event reports it (`costUsd` is the run's total so far), so every way a run can end keeps it; `task.cost` is `null` from the start of a run until then, meaning unknown, never $0. `taskTimeoutMin` stops a run and fails the task; so does `silenceTimeoutMin` when the run gives no output for that long (the `Runner` reports any stdout/stderr as `onActivity`). When a run fails, `Runner.classify` reads it with the provider's `errors` rules (`providers/errors.ts`: limit, auth, permission, other, plus the reset time); a limit or auth failure does not close the task: `Tasks.requeue` puts it back (up to `MAX_REQUEUES`, then it fails normally), keeps the session, and writes `state.providerHolds[provider]`, which `blockReason` turns into `providerLimit` / `providerAuth` for every agent on that CLI. A limit hold ends by itself at the reset time (or backoff) through `pump()`; an auth hold ends with `resumeProvider` (⚙️ Settings). `ProcessRunner.providers()` runs each CLI's `--version` (cached) for `health` / `available`. `settings.paused` (`Tasks.setPaused`, `POST /api/office/pause`) is the first block: running tasks finish, nothing starts, `Schedules.tick` gives nothing. Reports lower `depth`, so loops are bounded by counting per root chain (`shared/chain.ts`, used by `blockReason` and the task card): `chainMaxTurns` / `chainBudgetUsd` hold the chain's next task queued, and `runNext` skips such a task so it does not block the agent's other work. `Tasks.retry` creates a new task with the same `agentId`/`parentId`/`from`/`depth`/`kind` and `retryOf`: a held failure report is dropped, an unread one cancelled (after the retry exists, so a report held above does not release), and one already read makes the retry a `correction`, whose report replaces it; being a report it sends nothing further up. Retrying a root task starts a new chain. `application/approvals.ts`: an approval asked during a task counts as open work under it (`hasOpenUnder(tasks, id, pendingTaskIds)`), so the report is held; the decision is sent to the agent as a `kind: 'report'` task from `user` under the asking task, and finishing that releases the held report.

**Team tools over MCP.** Each agent process is connected to a standalone stdio MCP server, `src/mcp/office-mcp.ts`, with the `AGENT_ID`/`TASK_ID`/`OFFICE_URL` environment variables (started through `node_modules/.bin/tsx`; providers with `delegation: false`, e.g. Cursor, do not get it). It provides six tools (`list_team`, `delegate_task`, `task_status`, `request_approval`, `remember`, `recall`) and implements them by calling the main server's HTTP API (`/api/team`, `/api/delegate`, `/api/tasks/:id`, `/api/notes`) — so agents delegate to each other through the main server, not through MCP.

**Shared knowledge.** `settings.officeNotes` and pinned `state.notes` are added to every system prompt outside the `canDelegate` gate, so providers without MCP get them too; `src/shared/knowledge.ts` holds the size caps and decides what fits, for the server's prompts and the Knowledge tab alike. `application/knowledge.ts`: an agent's `remember` always creates an unpinned note, and pinning exists only on `PATCH /api/notes/:id`, which the MCP server never calls. Unpinned notes are returned only by `recall`, as text the server renders (`domain/knowledge.ts`), one line each under an unverified label, so a note cannot pass as pinned.

**Delegation/report chain.** When an agent calls `delegate_task`, a new task is created and linked into the chain with `parentId` (`MAX_DELEGATION_DEPTH = 4`). When a task finishes (`Reports.finish`), if queued/running subtasks remain under its chain (`hasOpenUnder`), the report is **held** (`awaiting = true`); when the last subtask finishes, `releasableAncestor` finds the held report and it is sent to whoever gave the original task (`from`) as a new task/message. This lets a team lead split the work across the team and give their boss a single report after merging the parts. Every way a task closes (run end, `cancel`, firing through `abandon`, restart) goes through `Reports.finish`, so held reports always get their chance; a cancelled task reports nothing itself, and a held report with nobody to send to (someone fired) passes the release on upward. `Tasks.cancelChain` closes a `subtree()` and drops its held reports and pending approvals without starting a run. `Tasks.reconcile()` runs at startup (it, not the state store, turns `running` tasks into errors): sending a report starts a paid run, so only chains whose last end is within `AUTO_RELEASE_WINDOW_MS` (24 h) send theirs; older ones stay `awaiting` with nothing open, which the client shows as stuck with a manual *Send report* (`Tasks.releaseReport`).

**The default company structure is generated programmatically in `src/shared/company/`**, not a hand-written agent list: `index.ts` holds the language-independent structure (teams, colors, tools, workflow order) and fills the per-language text (`tr.ts` / `en.ts`: names, roles, `focus`, `reads`, `merge`, `leadNote`, prompt templates) into `buildCompany(locale)`. Flow: CEO → Product Manager → (discovery + requirements with the Product team) → Analysis → Design → Development → Test leads in order, each lead distributing work to their team and merging it. All outputs are written under `docs/<request-code>/<stage>/` in the shared working directory (`workspace/` by default); each stage reads the previous ones. When changing the company text, mind the cross-consistency checks in `src/shared/company/company.test.ts` (run for every language): every name quoted in an agent's `prompt` must really be in the team, and the leads must appear in the PM's flow in order (increasing index).

**`src/shared/layout.ts` and `src/shared/catalog.ts` are pure modules independent of three.js** — the server (`Agents.relayout()`), the browser (`infrastructure/three/world.ts`) and the tests all import them. Do not add three.js or DOM dependencies to these two files. Grid space is shared: 1 cell = 1 unit, `(x, z)` is the top-left cell, and at rotation 0 the front faces +z. `layout.ts` picks a tier from the headcount (`TIERS`) and produces the desk/room/corridor layout by team; `catalog.ts` holds the furniture/grid geometry definitions (`CATALOG`, `cellsOf`, `seatPoint`, `solidGrid`).

**Client architecture (`src/client`).** Same layering as the server. `domain/` is pure view logic (`views.ts`: team grouping, stats, kanban columns, chat items; `agentForm.ts`; `format.ts`). `application/` is the Zustand store (`officeStore.ts`: state, event reducer, use-case actions) and the ports it depends on (`ports.ts`: `Gateway` for the HTTP API, `EventFeed` for SSE, `Stage` for the 3D view, `KeyValueStorage`). `infrastructure/` implements them: `httpGateway.ts`, `stageHolder.ts` (keeps what the office says until the lazily loaded 3D world attaches, then forwards) and `three/` (`world.ts`: scene and input; `avatar.ts`: characters; `pathfinding.ts`: A*; `furniture.ts`: low-poly models; `mergeStatics.ts`: folds furniture parts into one mesh per material, leaving invisible boxes for clicks). `presentation/` holds the React components (`App`, `Sidebar`, `TopBar`, `Inspector`, `StagePanel`, `Modals`, `AgentForm`, ...), which read the store through `useOffice(selector)` and call `useActions()`. `domain/attention.ts` derives what each agent needs from the CEO (`attentionOf`); the store recomputes it whenever its inputs change, keeps it in `attention` and passes it to `Stage.setAttention`, so nothing marks a sign as resolved by hand: it goes when its cause does (only failures can also be dismissed, per browser). `main.tsx` is the composition root. Selectors must return existing references (derive arrays with `useMemo`), otherwise Zustand re-renders in a loop.

**Tests** (`src/**/*.test.ts`, run with `npm test`) cover the task lifecycle and delegation/report chain (`application/tasks.test.ts`, scripted runner + fake isolation), worktrees against real git in a temp dir, schedules, the file browser's path safety, state backups and the client view derivations; they also exercise `layout.ts` across a wide matrix of headcounts/team distributions (no overlaps, within bounds, reachability from the entrance to every seat via 4-neighbor BFS) and verify the structural/cross-reference consistency in `company/`.
